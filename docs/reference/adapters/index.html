Adapters

An adapter connects Kommander to one part of your environment. Kommander uses three kinds of adapter:

  • A WAL adapter stores the Raft log. The WAL is the write-ahead log.
  • A communication adapter carries Raft messages between the nodes.
  • A discovery adapter tells a node where to find the other nodes.

You pick one of each when you create a node. Kommander keeps persistence, transport, and discovery pluggable, so you can use the storage and the network stack that your service already has. You can also write your own adapter.

Common choices:

SituationWALCommunicationDiscovery
Networked clusterRocksDbWAL, SqliteWAL, or external SolariumWALGrpcCommunication or RestCommunicationStaticDiscovery
Tests and simulationsInMemoryWALInMemoryCommunicationStaticDiscovery or DynamicDiscovery

WAL Adapters​

AdapterUse case
RocksDbWALDurable production-oriented storage backed by RocksDB. Detects lost acknowledged writes and storage corruption.
SqliteWALDurable embedded storage backed by SQLite shard databases. Does not run the detection checks that RocksDbWAL runs.
SolariumWALExternal durable adapter supplied by the SolariumDb.Kommander package. Implemented in .NET without the native RocksDB library.
InMemoryWALTests, simulations, and browser builds, where it is the only built-in WAL. It does no fsync, and data is lost when the process exits.
IWAL rocks = new RocksDbWAL("./data", "node-1", logger);
IWAL sqlite = new SqliteWAL("./data", "node-1", logger);
IWAL memory = new InMemoryWAL(logger);

SolariumWAL is maintained outside the Kommander repository. It implements the same IWAL contract and is passed directly to RaftManager:

using Solarium.Kommander;

IWAL solarium = new SolariumWAL(
    "/var/lib/node1/raft",
    "v1",
    logger,
    syncWrites: true
);

Its data directory is not compatible with a RocksDbWAL directory, even though both adapters expose the same logical Raft behavior. See Solarium WAL for setup, durability, metrics, migration cautions, and tuning ownership.

Choosing RocksDbWAL Or SqliteWAL​

With syncWrites: true, both adapters fsync the term and the vote before the vote reply, and fsync log writes before they acknowledge them. They differ in what a node can detect after a storage fault, and in how they store a vote:

BehaviorRocksDbWALSqliteWAL
Acknowledged-presence watermark: a restore that finds fewer entries than the node acknowledged quarantines the partitionYesNo, the check is inert
Sync ledger: detects a log file truncated or lost after its fsyncYesNo
Fail-stop on corruption: the engine refuses writes, and its partitions stop leading, voting, and acknowledgingYesNo
Compaction floor that survives a restartYesNo, it reports 0

The missing checks mean LostAcknowledgedEntriesPolicy never triggers on SqliteWAL, and GetPartitionStorageHealth never reports LostAcknowledgedEntries or EngineFailed for it. Choose RocksDbWAL when you want the node to detect and refuse to serve from damaged storage.

RocksDB Shared Memory Resources​

Hosts that also open their own RocksDB database can share RocksDB memory resources with Kommander's RocksDbWAL.

using Kommander.WAL;

RocksDbSharedResources shared = RocksDbSharedResources.CreateWithUnifiedBudget(
    totalBytes: 512L * 1024 * 1024,
    memtableBudgetBytes: 128L * 1024 * 1024
);

IWAL rocks = new RocksDbWAL(
    path: "./data",
    revision: "node-1",
    logger: logger,
    syncWrites: true,
    sharedResources: shared
);

The bundle contains one shared RocksDB block cache and one shared write-buffer manager. RocksDbWAL borrows the bundle; the host owns it and disposes it after all databases that use it have closed.

There is no RaftConfiguration flag for this. Sharing is configured by passing sharedResources to the RocksDbWAL constructor and wiring the same cache/write-buffer manager into the host application's own RocksDB options before opening that database.

See Shared RocksDB Memory for sizing, ownership, and observability guidance.

RocksDB WAL Tuning​

RocksDbWAL also accepts a RocksDbWalTuning object for deployments with unusual log rates, many hot partitions, or a tight shared RocksDB memory budget:

IWAL rocks = new RocksDbWAL(
    path: "./data",
    revision: "node-1",
    logger: logger,
    syncWrites: true,
    tuning: RocksDbWalTuning.Default
);

The defaults are designed for append-heavy Raft logs whose dead prefix is deleted logically and then reclaimed as whole SST files.

PropertyDefaultDescription
ShardWriteBufferSizeBytes64 MiBSize of one Raft-log shard column-family memtable.
ShardMinWriteBufferNumberToMerge2Immutable memtables merged into one flush. This widens the window where short-lived log rows and their tombstones can die before reaching disk.
ShardMaxWriteBufferNumber4Maximum mutable plus immutable memtables per shard column family. Must be greater than ShardMinWriteBufferNumberToMerge.
ShardLevel0FileNumCompactionTrigger8L0 file count that triggers movement toward the base level. Under the floor layout, non-overlapping partition files usually move without rewriting rows.
ShardLevel0SlowdownWritesTrigger28L0 file count where RocksDB begins slowing writers.
ShardLevel0StopWritesTrigger44L0 file count where RocksDB stops writers.
MaxTotalWalSizeFlushUnits2Bound for live RocksDB .log files, measured in shard flush units. Keeps idle or trickle-write column families from pinning an unbounded WAL replay tail. 0 leaves RocksDB's default.
ShardMaxBytesForLevelBase0Optional RocksDB max_bytes_for_level_base override for shard column families. 0 leaves the RocksDB default.
ShardUniversalCompactionfalseUses universal compaction for shard column families instead of the shipped leveled layout.

When you share a WriteBufferManager, size its budget for at least the Raft WAL flush unit plus the host database's own memtables. The flush unit is ShardWriteBufferSizeBytes * ShardMinWriteBufferNumberToMerge; the writer also needs one additional mutable memtable of headroom. If the shared budget is too small, RocksDB flushes early and write amplification rises even though safety is unchanged.

MaxTotalWalSizeFlushUnits applies to the RocksDB engine's own write-ahead .log files, not to Raft log entries. RocksDB can only delete a .log file after every column family with data in that file has flushed. The cap lets RocksDB flush the small pinning column families before restart replay grows without bound, while busy shard column families continue to flush on their normal Raft-log cadence.

SqliteWAL uses a fixed pool of SQLite shard databases. Partitions map to shards with partitionId mod shardCount, so FairWalScheduler group batches can be committed as one transaction per shard instead of one transaction per partition.

You can choose the shard count for a fresh WAL directory:

IWAL sqlite = new SqliteWAL(
    path: "./data",
    revision: "node-1",
    logger: logger,
    syncWrites: true,
    shardCount: 4
);

Use fewer shards when write batching and fsync reduction matter most. Use more shards when independent SQLite shard concurrency matters more. The shard count is persisted the first time the directory is initialized; changing it later would remap partitions, so reopening an existing directory with a different non-zero shard count fails fast. This argument is the only control: RaftConfiguration.SqliteWalShardCount has no effect.

Both durable adapters also support syncWrites: false for benchmarks and some CI scenarios:

IWAL fastRocks = new RocksDbWAL("./data", "node-1", logger, syncWrites: false);
IWAL fastSqlite = new SqliteWAL("./data", "node-1", logger, syncWrites: false);

With syncWrites: false, acknowledged writes may still be lost on process or machine crash. Use that mode only when crash durability is not part of what you are validating.

Custom WAL Adapters​

Custom adapters implement IWAL.

public interface IWAL : IDisposable
{
    List<RaftLog> ReadLogs(int partitionId);
    List<RaftLog> ReadLogsRange(int partitionId, long startLogIndex, int maxEntries = int.MaxValue);
    List<RaftLog> ReadLogsRange(int partitionId, long startLogIndex, int maxEntries, long maxBytes);
    long GetTermAt(int partitionId, long logIndex);
    RaftOperationStatus Write(List<(int, List<RaftLog>)> logs);
    RaftOperationStatus Write(List<(int, List<RaftLog>)> logs, bool sync);
    RaftOperationStatus Write(
        List<(int, List<RaftLog>)> logs,
        bool sync,
        IReadOnlyDictionary<int, long>? acknowledgedPresence
    );
    long GetAcknowledgedPresence(int partitionId);
    bool SetAcknowledgedPresence(int partitionId, long value);
    string? GetFailStopReason();
    string? GetLostSyncedWritesReason(int partitionId);
    bool MarkLostSyncedWritesReconciled(int partitionId);
    long GetMaxLog(int partitionId);
    long GetCurrentTerm(int partitionId);
    long GetLastCheckpoint(int partitionId);
    long GetCompactionFloor(int partitionId);
    int CountPersistedLogs(int partitionId);
    int CountRemovableLogs(int partitionId);
    string? GetMetaData(string key);
    bool SetMetaData(string key, string value);
    bool PersistHardState(int partitionId, long currentTerm, string? votedFor);
    bool TryGetHardState(int partitionId, out long currentTerm, out string? votedFor);
    bool PersistHlcFloor(int partitionId, long floorL);
    long GetHlcFloor(int partitionId);
    (RaftOperationStatus Status, int Removed) CompactLogsOlderThan(
        int partitionId,
        long lastCheckpoint,
        int compactNumberEntries,
        int? maxTotalEntries = null
    );
    RaftOperationStatus DeletePartitionWAL(int partitionId);
    RaftOperationStatus TruncateLogsAfter(int partitionId, long afterLogId);
    (RaftOperationStatus Status, long MaxLogId) TruncateLogsAfterAndGetMax(int partitionId, long afterLogId);
    RaftOperationStatus TruncateProposedLogsAfter(int partitionId, long afterLogId);
    (RaftOperationStatus Status, bool SuffixTruncated) InstallSnapshotBoundary(
        int partitionId,
        long snapshotIndex,
        long lastIncludedTerm,
        bool sync
    );
}

Every adapter must follow this concurrency contract:

  • All methods must be safe to call from several threads at once on the same instance.
  • A read for a partition must observe every write that completed before the read began.
  • Write is atomic per partition: all of a partition's logs in the batch persist, or none do. It overwrites an entry with the same partition and id. Atomicity across partitions depends on the adapter: RocksDbWAL writes one atomic batch, and SqliteWAL commits one transaction per shard.
  • RaftLog.Id orders a partition's log, not insertion order. Every read path must return logs sorted by id, ascending.
  • TruncateLogsAfterAndGetMax must delete and read the max under one acquisition of the write guard, so no concurrent write lands between them.
  • DeletePartitionWAL must be idempotent and must not touch another partition.

Return values also carry meaning. GetCurrentTerm returns the term of the entry with the highest id, or 0 when the partition is empty. GetMaxLog returns 0 when it is empty. GetLastCheckpoint returns -1 when no committed checkpoint exists.

Several methods have default implementations in the source interface to keep simple test adapters compatible. A durable adapter must not keep these two defaults, because they can lose data:

  • TruncateProposedLogsAfter defaults to the blanket TruncateLogsAfter. Followers call it to clean up an append's tail, and entries can arrive out of order, so a blanket delete can remove committed entries that already landed. That loses quorum-acknowledged data and leaves a replica that reports a committed frontier above a hole. Delete only Proposed and ProposedCheckpoint entries.
  • InstallSnapshotBoundary defaults to a non-atomic sequence of GetTermAt, TruncateLogsAfter, and Write, intended for test fakes. Install the boundary in one atomic transaction or batch, and honor sync. The method must decide whether to keep or truncate the suffix itself, from the stored term at snapshotIndex.

The other defaults are safe, but some cost performance or turn off a check:

  • ReadLogsRange(..., maxBytes) can delegate to the entry-count overload, but durable adapters should enforce the byte cap during the scan so backfill does not materialize oversized batches.
  • Write(..., sync) can delegate to Write(...); durable adapters should honor sync: false for commit-marker batches used by the single-fsync fast path.
  • GetTermAt can use ReadLogsRange, but durable adapters should implement a scalar lookup so log-matching checks do not read payloads.
  • PersistHardState and TryGetHardState use metadata keys by default. A durable adapter's SetMetaData must therefore fsync before it returns true, under its configured syncWrites. A vote that reaches the candidate but not the disk lets the node grant a second candidate the same term after a power loss: two leaders in one term, and committed entries overwritten. SetMetaData must also return false on storage failure instead of throwing, because election code will not solicit votes or grant a vote that it could not record.
  • PersistHlcFloor and GetHlcFloor use metadata keys by default. On restore, Kommander merges the floor into the local hybrid logical clock before it can mint new proposal timestamps.
  • Write(logs, sync, acknowledgedPresence), GetAcknowledgedPresence, and SetAcknowledgedPresence default to keeping no watermark, which makes the lost-entries check inert. To support it, write the watermark atomically with the rows, and clamp it on every path that removes rows, or the next restore reports a loss that never happened.
  • GetFailStopReason defaults to null, meaning the adapter never fail-stops. Return a non-null reason after a fault that the adapter must not try to recover from. The node then steps the partitions down and stops them voting and acknowledging.
  • GetLostSyncedWritesReason and MarkLostSyncedWritesReconciled default to keeping no record outside the log, so a log truncated after its fsync goes undetected.
  • GetCompactionFloor defaults to 0, which tells the caller nothing. Reporting a floor that survives a restart lets a restored node avoid a needless snapshot.

The counting methods are useful for tests, diagnostics, and compaction visibility:

  • CountPersistedLogs: total persisted log rows for the partition.
  • CountRemovableLogs: persisted rows strictly below the last committed checkpoint.

Communication Adapters​

AdapterUse case
GrpcCommunicationNetworked clusters using gRPC streaming.
RestCommunicationNetworked clusters using REST/JSON endpoints.
InMemoryCommunicationUnit tests and in-process simulations.

Outbound Raft transport messages can be batched through BatchRequests. That includes append traffic and control traffic such as step-down notices and leadership-transfer requests.

RestCommunication uses source-generated System.Text.Json metadata for its Raft request and response bodies. This keeps the REST wire shape stable while supporting trimmed hosts that disable reflection-based JSON. If you build a custom REST host or add new REST message types, make sure every request and response type is present in the generated JSON context; one missing type can make the host fail when ASP.NET Core builds the endpoints.

The browser/thread-free build keeps the REST client, but leaves out server transports and the gRPC client. See Thread-Free Embedded Mode for the browser target limits.

Custom transports implement ICommunication.

Nine methods have no default, so a transport does not compile without them: Handshake, RequestVotes, Vote, AppendLogs, CompleteAppendLogs, BatchRequests, SendJoin, SendLeave, and SendSetMemberRole.

The other eight have defaults that return a failure or do nothing. Relying on a default disables the runtime behavior behind it:

MethodEffect of keeping the default
SendPing, SendPingReqEvery SWIM probe counts as failed.
SendGossipNo membership anti-entropy, and no load reports reach peers.
GetRemoteFollowerLagLearner promotion skips the lag check for partitions led elsewhere.
SendInstallSnapshotA follower below the leader's compaction floor stays stuck.
NotifyJoinBlockedThe joiner is not told that promotion is blocked, so it waits for JoinPromotionStallTimeout.
GetReadIndexConfirmLocalApplicationAsync returns false on every non-leader.
ForwardReplicateLogsA node that does not host a partition cannot forward a proposal, so ReplicateLogs throws PartitionNotHostedException.

On the receive side, your host passes inbound requests to RaftManager. Use the IRaft transport entry points, plus ReceiveJoin, ReceiveLeave, ReceiveSetMemberRole, ReceiveInstallSnapshot, ReceiveGossip, ReceivePing, ReceivePingReq, and ReceiveGetReadIndex.

InMemoryCommunication includes fault-injection controls for tests and simulations:

  • PartitionNode(endpoint) drops all traffic to and from one endpoint
  • HealPartition(endpoint) restores traffic for a node partition
  • BlockLink(from, to) drops only one directed link
  • UnblockLink(from, to) restores one directed link
  • BlockLinkBothWays(a, b) and UnblockLinkBothWays(a, b) model a pairwise network cut
  • HealAll() removes every node and link filter.

Directional link blocks are useful for testing asymmetric networks. A request can reach a peer while the reply is lost, which models failures such as a snapshot install that succeeds on the receiver while the sender observes a failed transfer.

Dynamic Membership Support​

The built-in transports do not all implement the same methods:

CapabilityMethodInMemoryCommunicationGrpcCommunicationRestCommunication
Join, leave, and role changesSendJoin, SendLeave, SendSetMemberRoleYesYesYes
SWIM probesSendPing, SendPingReqYesYesYes
Membership gossip and load reportsSendGossipYesYesYes
Remote lag lookup for learner promotionGetRemoteFollowerLagYesYesYes
Snapshot installationSendInstallSnapshotYesYesYes
Follower read indexGetReadIndexYesYesNo
Blocked-join notificationNotifyJoinBlockedYesNoNo
Proposal forwardingForwardReplicateLogsYesNoNo

The last three rows change behavior in production:

  • On RestCommunication, ConfirmLocalApplicationAsync fails closed: it returns false on every non-leader. Use GrpcCommunication if a follower must confirm that its applied state has caught up.
  • On gRPC and REST, a joiner whose promotion is permanently blocked does not hear about it. JoinCluster with seeds waits for JoinPromotionStallTimeout and throws TimeoutException, instead of failing at once.
  • On gRPC and REST, a node cannot forward a proposal for a partition it does not host. Route writes to a replica with GetPartitionReplicas, and handle PartitionNotHostedException.

Discovery Adapters​

AdapterUse case
StaticDiscoveryFixed seed/contact list. Useful for bootstrap, not as the live membership authority.
DynamicDiscoveryMutable in-memory contact list controlled by the application. Useful for tests and programmatic bootstrap.
MulticastDiscoveryUDP multicast discovery on local networks, on the fixed group and port 239.0.0.222:1900. Host must parse as an IP address. If the listener fails, it only writes to the console and stops, so the node finds no peers and Register reports no error.

RedisDiscovery is present in source as a placeholder and returns no nodes in this release. Do not use it for cluster formation.

Custom discovery providers implement IDiscovery:

public interface IDiscovery
{
    Task Register(RaftConfiguration configuration);
    List<RaftNode> GetNodes();
}

Discovery helps nodes find contact points. The committed roster on partition 0 remains the source of truth for who actually belongs to the cluster and who counts toward quorum.
